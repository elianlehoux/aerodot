# Flowdot: plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construir Flowdot en `/flowdot`: cargar la foto de una cabina, armar flujos de pasos numerados, mirarlos, repasarlos de memoria y compartirlos con un archivo `.flowdot`, todo guardado en el dispositivo.

**Architecture:** Una sola página Astro (`src/pages/flowdot.astro`) monta una app de JS propio que vive en `src/flowdot/`. La lógica pura (geometría, edición, repaso, archivo, rutas) está separada del DOM y se prueba con `node --test`. La interfaz es una imagen con un SVG encima dentro de un contenedor que se mueve con `transform`; los datos van a IndexedDB.

**Tech Stack:** Astro 6, JS propio sin framework, SVG, IndexedDB, `createImageBitmap` y `OffscreenCanvas`, `pdfjs-dist` (cargado solo al subir un PDF), `node --test`.

**Spec:** `docs/superpowers/specs/2026-11-16-flowdot-design.md`. Leerlo entero antes de empezar. Las secciones se citan como "spec 4.5".

## Global Constraints

- Node 22.12 o superior. Antes de cualquier comando: `source ~/.nvm/nvm.sh && nvm use 24`.
- Solo pnpm. La única dependencia nueva es `pdfjs-dist`.
- No hacer commit ni push. Al final de cada tarea los cambios quedan en el árbol de trabajo. Donde una skill de ejecución pida "commit", se reemplaza por correr `pnpm build && pnpm test`.
- Nada de lo que se hizo para Inglés o la Biblioteca se reutiliza dentro de la app (`aircraft-views.js`, `maneuvers.js`, `english*.css`). Sí se usan los tokens de `global.css`, `BaseLayout.astro` y `BrandMark.astro`.
- Un solo acento: `--accent`. La ruta y los puntos van en `--accent`. Verde y rojo solo para el ✓ y el ✗ del repaso.
- Textos de interfaz: español rioplatense con voseo, mayúscula solo al inicio, sin emojis, sin rayas largas (—).
- Ruta `/flowdot`. Nombre visible "Flowdot".
- Valores fijos del spec: lado mayor de la imagen 2560 px; WebP calidad 0,85 (JPEG si no hay WebP); radio de acierto 28 px en pantalla; toque = menos de 10 px y menos de 300 ms; guardado 400 ms después del último cambio; Mirar cada 0,8 s; aviso de copia a los 30 días; nombres hasta 120 caracteres; hasta 200 pasos por flujo; archivo `format: "flowdot"`, `version: 1`.
- Metas de rendimiento (spec 6): JS propio de Flowdot menos de 30 KB comprimido sin contar pdf.js, PostHog ni Sentry; respuesta a un toque menos de 16 ms; foto de 12 MP menos de 300 ms en computadora y menos de 1 s en teléfono; abrir un flujo menos de 100 ms.
- La foto, los nombres y las posiciones nunca salen del dispositivo, salvo en el archivo que la persona comparte. El contenedor de la app lleva la clase `ph-no-capture`.
- Controles táctiles de 44 px o más. Sin desplazamiento horizontal desde 320 px de ancho. Con `prefers-reduced-motion: reduce` no se anima el trazo.

## Review Focus

1. Dos pasos más cerca que el radio de acierto: el toque cuenta para el más cercano, no para el primero de la lista. Prueba en Tarea 1.
2. Foto vertical, foto chica (menos de 2560 px) y foto de iPhone con orientación EXIF: las medidas finales respetan la proporción, no se agranda una foto chica y la orientación es la que se ve en la galería. Prueba de `fitWithin` en Tarea 1; orientación en la verificación manual de Tarea 6.
3. Archivo importado con ids repetidos dentro del mismo archivo o con un flujo cuyo id ya existe en otra cabina: entran con ids nuevos y no se pisa nada. Prueba en Tarea 4.
4. Flujo sin pasos en Mirar y en Repasar: el repaso termina enseguida con resumen en cero y los botones de reproducir quedan desactivados, sin errores. Prueba en Tarea 3.
5. Navegador que rechaza guardar (cuota llena o modo privado): se avisa una vez y lo que hay en pantalla no se pierde mientras la página siga abierta. Verificación manual en Tarea 5.

### Tarea 1: Geometría

**Files:**
- Create: `src/flowdot/geometry.js`
- Test: `test/flowdot-geometry.test.mjs`

**Interfaces:**
- Produces:
  - `type View = { scale: number, tx: number, ty: number, width: number, height: number }` (width y height: tamaño de la imagen guardada en px; pantalla = imagen × scale + t).
  - `toFraction(px: number, py: number, view: View): { x: number, y: number }`
  - `toScreen(x: number, y: number, view: View): { px: number, py: number }`
  - `hitTest(steps: Step[], px: number, py: number, view: View, radius = 28): number` índice del paso más cercano dentro del radio en pantalla, o -1.
  - `classifyGesture(dx: number, dy: number, ms: number): 'tap' | 'drag'`
  - `fitWithin(width: number, height: number, max = 2560): { width: number, height: number }`
  - `routePath(points: Array<{px: number, py: number}>): string` atributo `d` del SVG.

- [ ] **Paso 1: Escribir las pruebas**

```js
test('toFraction y toScreen son inversas con zoom y desplazamiento', () => {
  const view = { scale: 1.75, tx: -120, ty: 40, width: 2560, height: 1707 };
  const { x, y } = toFraction(500, 300, view);
  const back = toScreen(x, y, view);
  assert.ok(Math.abs(back.px - 500) < 1e-9 && Math.abs(back.py - 300) < 1e-9);
});
test('hitTest: dos pasos dentro del radio, gana el más cercano', () => {
  const view = { scale: 1, tx: 0, ty: 0, width: 1000, height: 1000 };
  const steps = [{ x: 0.100, y: 0.1 }, { x: 0.120, y: 0.1 }];
  assert.equal(hitTest(steps, 118, 100, view), 1);
});
test('hitTest: el radio se mide en pantalla, no en la imagen', () => {
  const steps = [{ x: 0.5, y: 0.5 }];
  assert.equal(hitTest(steps, 527, 500, { scale: 1, tx: 0, ty: 0, width: 1000, height: 1000 }), 0);
  assert.equal(hitTest(steps, 529, 500, { scale: 1, tx: 0, ty: 0, width: 1000, height: 1000 }), -1);
  assert.equal(hitTest(steps, 1027, 1000, { scale: 2, tx: 0, ty: 0, width: 1000, height: 1000 }), 0);
});
test('classifyGesture: 9 px en 200 ms es toque; 10 px o 300 ms es arrastre', () => {
  assert.equal(classifyGesture(6, 6.9, 200), 'tap');
  assert.equal(classifyGesture(10, 0, 100), 'drag');
  assert.equal(classifyGesture(0, 0, 300), 'drag');
});
test('fitWithin: achica el lado mayor a 2560 y respeta la proporción', () => {
  assert.deepEqual(fitWithin(4032, 3024), { width: 2560, height: 1920 });
  assert.deepEqual(fitWithin(3024, 4032), { width: 1920, height: 2560 });
});
test('fitWithin: una foto chica no se agranda', () => {
  assert.deepEqual(fitWithin(1200, 800), { width: 1200, height: 800 });
});
test('routePath: vacío con menos de 2 puntos, empieza en el primero', () => {
  assert.equal(routePath([{ px: 1, py: 1 }]), '');
  assert.match(routePath([{ px: 10, py: 20 }, { px: 50, py: 60 }, { px: 90, py: 20 }]), /^M10 20 C/);
});
```

### Tarea 3: Motor del repaso

**Files:**
- Create: `src/flowdot/review.js`
- Test: `test/flowdot-review.test.mjs`

**Interfaces:**
- Produces:
  - `createReview(steps: Step[], { mode: 'order' | 'where', only?: string[], random?: () => number }): ReviewState`. `only` limita a esos ids conservando el orden original. En `'where'` el orden se mezcla con `random`.
  - `reviewTap(state, hitIndex: number): { state: ReviewState, result: 'hit' | 'miss' }`. `hitIndex` es el índice en `steps` que devolvió `hitTest`; acierta si es el paso esperado.
  - `reviewHint(state): ReviewState` sube el nivel de ayuda del paso actual: 0, 1 (zona), 2 (punto). No pasa de 2.
  - `ReviewState` expone `{ current: number, total: number, expectedIndex: number, hintLevel: 0|1|2, done: boolean }`.
  - `reviewSummary(state): { total, firstTry, errors, hints, missedStepIds: string[] }`. `missedStepIds`: pasos con al menos un error o una ayuda, en el orden original.

- [ ] **Paso 1: Escribir las pruebas:** con 3 pasos, hit, miss, hit, hit da `{ total: 3, firstTry: 2, errors: 1, hints: 0, missedStepIds: [id2] }` y `done`; un miss no avanza `current`; `reviewHint` dos veces da `hintLevel 2`, una tercera sigue en 2, y al acertar el siguiente paso arranca en 0; un paso con ayuda y sin error cuenta en `hints` y en `missedStepIds` pero no en `firstTry`; `only: [id3, id1]` repasa id1 y después id3; `'where'` con `random` fijo da un orden distinto del original pero con los mismos ids; **flujo sin pasos**: `createReview([], …)` da `done: true` y `reviewSummary` todo en 0.

### Tarea 4: Archivo `.flowdot`

**Files:**
- Create: `src/flowdot/file.js`
- Test: `test/flowdot-file.test.mjs`

**Interfaces:**
- Produces:

  - `parseFlowdot(text: string): { ok: true, entries: Array<{ cabin, flows }> } | { ok: false, error: string }`. Al leer, `cabin.image.blob` es un `Blob` armado desde el base64. El error es una frase en español que nombra la parte mala (ej.: `"El paso 4 del flujo «Antes de despegar» tiene una posición fuera de la imagen."`).
  - `planImport(entries, existing: { cabinIds: Set<string>, flowCabin: Map<string, string> }, decide: (cabin) => 'update' | 'copy' | 'skip', newId: () => string): Array<{ type: 'putCabin', cabin } | { type: 'putFlow', flow }>`. Nunca produce borrados.
  - `fileNameFor(name: string): string` y `backupFileName(date: Date): string`.

- [ ] **Paso 1: Escribir las pruebas:**
  - Ida y vuelta: `exportFlowdot` de una cabina con 2 flujos y `parseFlowdot` del resultado devuelven los mismos nombres, pasos y bytes de imagen.
  - Rechazos, cada uno con `ok: false` y un mensaje que nombra la parte: `format` distinto, `version: 2`, JSON roto, `x: 1.2`, label de 121 caracteres, 201 pasos, imagen sin `data`, `type` fuera de `image/webp|jpeg|png`.
  - `planImport` con `'update'`: la cabina y los flujos del archivo se ponen; un flujo guardado de esa cabina que no está en el archivo no aparece en las operaciones (no se borra).
  - `planImport` con `'copy'`: ids nuevos para cabina y flujos, `cabinId` de los flujos apunta al id nuevo, nombre con `" (copia)"`.
  - `planImport` con `'skip'`: ninguna operación para esa cabina.

  - Cabina sin conflicto: entra con sus ids y `decide` no se llama.
  - `fileNameFor('Cessna 152 LV-ABC')` es `'cessna-152-lv-abc.flowdot'`; `fileNameFor('Ñandú / Piper')` es `'nandu-piper.flowdot'`; `backupFileName(new Date('2026-11-16T12:00:00Z'))` es `'flowdot-copia-2026-11-16.flowdot'`.
